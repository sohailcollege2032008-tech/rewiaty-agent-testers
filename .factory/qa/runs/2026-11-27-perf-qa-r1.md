## 3. تحليل الاختناقات

### 3.1 فتح كتاب كبير (200k كلمة) — المسار الكامل

الترتيب المؤكد من الكود والقياس:

1. **`readBookBundle` بتعيد `parseBook` في كل فتحة** — `apps/mobile/src/storage/bundle.ts:166`. مفيش كاش للـ `Book` المُحلّل، ولا للـ manifest/الفصول. في Node (warm، 5 رنات) على نفس الهوست:
   - 57.8k كلمة: **329 ms** (median، بدون تنظيف عربي) / 415 ms (بتنظيف)
   - 200k كلمة: **571 ms** / **870 ms**
2. **الكتاب كله بيتبعت للـ WebView** كـ `{type:'load', book}` — `apps/mobile/src/screens/reader-screen.tsx:467` (و`:348`). الـ JSON المقيس: 401 KB (57.8k) و1,995 KB (200k)، و`JSON.stringify` نفسها 4.7 ms / 25 ms — **الـ serialization مش هو المشكلة**، المشكلة إن الـ object الكامل (8,318 block + 60 فصل) بيتبني ويعبر الـ bridge في كل فتحة، وبيتحسب تاني في كل مرة.
3. **الـ pagination في الـ engine** هي الجزء الأكبر: بعد ما الـ engine يبقى ready (395 ms)، أول موضع بياخد **4582–6458 ms** للـ 200k، بينما `layout_complete` = 2111–2524 ms — يعني **~2.5 ثانية زيادة بين "الـ layout خلص" و"أول موضع اتحسب"** (حساب الصفحات/الانتشار على 1,532 صفحة).
4. النتيجة على الجهاز: أول فريم 5.2–7.7 ثانية، مقابل هدف 2 ثانية. وعلى الـ CI runner (أسرع وأهدى) الرحلة سجّلت **2893 ms** — أي إن حتى في أحسن ظرف إحنا **+45%** فوق الهدف.

**الترتيب المقترح للتحسين (بدون كسر أي عقد):**
- كاش `parseBook` داخل `readBookBundle` (مذكورة بالفعل كتذكرة في `.factory/FEATURES.md:37`) — بيوفّر 0.6–0.9 ثانية + إعادة بناء الـ object كل فتحة. أرخص مكسب وأقل مخاطرة.
- بعدها: الـ pagination — قياس الصفحات بشكل تدريجي (أول N صفحة بس قبل أول فريم) بدل ما تحسب 1,532 صفحة قبل ما تعرض حاجة.

### 3.2 حجم الـ APK

- **29 مكتبة native = 61% من الـ APK المضغوط.** أي شغل على الـ JS أو الأصول هيحرّك أرقام صغيرة (JS bundle 3.9 MB، خط `res/P1.ttf` 0.93 MB)، والـ native هو الحد.
- النسخة الـ arm64 لوحدها **41.47 MB** — يعني حتى بعد ما نشيل باقي الـ ABIs إحنا لسه فوق 40 بالـ MB (وتحت بالـ MiB). الحد 40 MB بالـ MB صعب يتحقق من غير تقليل مكتبات native نفسها (أو ضغط أفضل للـ `.so`، أو شيل مكتبات مش مستخدمة).
- **الحاجة العملية**: الـ universal 70 MB — لو ده اللي بيتوزّع فعلاً للمستخدم (زي ما هو مثبّت على الجهاز)، فإحنا +75% فوق الحد. أول خطوة هي التأكد إن مسار التوزيع بياخد `arm64` بس (ABI split)، وبعدها نقلّل الـ native.

## 4. Findings

كل Finding فيها: الشدة حسب سلم `perf-qa` (P1 = فشل تحت الحمل المستهدف أو ضياع داتا · P2 = تعدّي الحد بأكتر من 50% · P3 = الباقي)، والمالك، والرقم مقابل الحد، وأمر إعادة القياس.

### F1 — الـ APK الـ universal 70.0 MB مقابل حد 40 MB (P2)
- **المالك:** `lane:L5` (build/APK + `bundle.ts`)
- **الرقم:** 70,084,923 بايت = 70.0 MB (66.83 MiB) — **+75%**. نسخة arm64 وحدها 41.47 MB (39.55 MiB) = +3.7% بالـ MB.
- **السبب:** 29 مكتبة native (25.47 MB مضغوط) مضروبة في كل ABI داخل الـ universal.
- **إعادة القياس:** `stat -c%s .factory/evidence/latest/apk/app.apk && unzip -l .factory/evidence/latest/apk/app.apk | tail -1`

### F2 — 18.6% من فريمات تقليب الصفحة janky مقابل حد 5% (P2، مع تحفّظ بيئة)
- **المالك:** `lane:L4` (reader engine — رسم/قياس الصفحة أثناء التقليب)
- **الرقم:** median 18.60% (3 رنات: 32.95 / 18.60 / 7.06)، p95 32.95%، p99 للفريم 250–450 ms.
- **التحفّظ:** نفس الهوست كان load 19–35، وفي Chrome نفس التقليبات p95 25.8–56.6 ms. جزء من الـ jank هو WebView/هوست. **لو اتقاس على runner هادي وفضل فوق 5% يترقّى P2 مؤكد، ولو نزل تحته يتحوّل P3.**
- **إعادة القياس:** `adb shell dumpsys gfxinfo com.rewiaty.app reset` ثم 15 `adb shell input swipe 600 760 100 760 300` ثم `adb shell dumpsys gfxinfo com.rewiaty.app | sed -n '/Janky frames/,+6p'`

### F3 — فتح كتاب 200k كلمة 4.9–6.5 ثانية مقابل هدف 2 ثانية (P2)
- **المالك:** `lane:L4` (pagination في الـ engine) + مساهمة `lane:L5` (`readBookBundle` بتعيد `parseBook` كل فتحة)
- **الرقم:** أول موضع median **4927 ms** / p95 6458 ms، أول فريم median 5296 ms / p95 7696 ms؛ وعلى CI runner **2893 ms** (run `45846756202`، والجولة اللي قبلها 2393–2460). **+45% إلى +223%.**
- **القطع المؤكدة:** parse 571–870 ms (Node، 200k) · جسر `{type:'load'}` بـ 1,995 KB JSON · الـ pagination ~2.5 ثانية بعد اكتمال الـ layout لـ 1,532 صفحة.
- **إعادة القياس:** `with-e2e-lock node $S/bench-engine.mjs` (بيطبع `first_position_ms` و`layout_complete_ms` لكل كتاب)، وللرحلة الرسمية: `with-e2e-lock bash scripts/ci-flows.sh long-book-open`

### F4 — Cold start 3958 ms مقابل حد 2500 ms (P3، مش attribut-able)
- **المالك:** `lane:L5`
- **الرقم:** median 3958 ms على 10 رنات (جلسة A 3128، جلسة B 4205)، أفضل رن 2349، p95 4968. **+58%**، بس الفارق بين الجلستين نفسه 34% بسبب الحمل.
- **إعادة القياس:** الأمر في جدول #1، **واشترط load < 2 على 8 أنوية** وإلا الرقم مش مقارن.

### F5 — ذاكرة القارئ 319.4 MB مقابل حد 250 MB (P3)
- **المالك:** `lane:L4` (حجم DOM/الصفحات المحسوبة في الـ engine بعد الفتح)
- **الرقم:** 276.0 MB (57.8k) و**319.4 MB PSS / 448.5 MB RSS** (200k)، مقابل 133.4 MB في المكتبة. **+28%**. الـ JS heap نفسه 6.4 / 19.1 MB بس — الباقي WebView + الـ DOM (3,178 node للـ 200k).
- **إعادة القياس:** `adb shell dumpsys meminfo com.rewiaty.app | grep -E "TOTAL PSS|TOTAL RSS"` والقارئ مفتوح على الكتاب الكبير.

### F6 — نسخة arm64 = 41.47 MB مقابل حد 40 MB (P3)
- **المالك:** `lane:L5`
- **الرقم:** 41,473,435 بايت = 41.47 MB (+3.7%) بحساب MB، و39.55 MiB (تحت الحد) بحساب MiB.

## 5. حدود الجولة (مش نتايج)

- **10 رنات cold start و3 رنات jank بس** على هوست load 19–35 — مش رقم نظيف، والـ app اتقتل بالـ LMK كذا مرة أثناء القياس.
- **الـ universal هو المثبّت** مش arm64؛ كل قياسات الذاكرة/الزمن/الـ jank على الـ universal.
- **`app-lab` drag** مش بيوصل لضغطة-لحركة < 350 ms (بيتحوّل long-press ويعلّم نص)، فالتقليب اتعمل بـ `adb shell input swipe`.
- **كتاب «أمواج»** (57,867 كلمة) استُخدم للاختبار المحلي بس: مستورد على الجهاز بـ `ACTION_VIEW file:///data/local/tmp/amwaj.md` (MediaStore `content://` فشل بـ «تعذّر فتح الكتاب»)، **واتمسح من الجهاز في آخر الجولة** (`pm clear com.rewiaty.app` + `rm`) — مش دخل الريبو ولا أي commit. الكتاب المولَّد 200k (`long-ar-200k.md`) في الـ scratch برضه، مش في الريبو.
- **الرحلة `long-book-open` في run `45906206340`** فشلت بخطأ assertion (نص غير ظاهر) مش بتوقيت — مسار تاني، مش موضوع التقرير، بس يستاهل lane:L5 يبص عليه.
